# AI Generation System Documentation

> **Last updated**: 2026-05-30
> **Database**: All media stored in `data/media/media.db.sqlite` (`media_assets` table)

## Overview

PipelineGen integrates Google Vids, NVIDIA Flux, and Ollama to generate images enriched with
LLM-generated semantic metadata. Assets are deduplicated, indexed for hybrid search, and uploaded to Google Drive.

- **Deduplication**: SHA-256 hashing to avoid duplicate files
- **Database**: `media.db.sqlite` (`media_assets` table) — unified for images, videos, audio, voiceovers
- **Google Drive**: Automatic upload with `metadata.json` sidecar
- **Semantic Enrichment**: LLM-generated `concept_tags`, `visual_objects`, `emotional_tone`, `search_text_expanded` via Ollama at ingest time (not at search time)

## Image Generation

### Models Available
- `FLUX.1-schnell` — fast generation (default, via NVIDIA cloud)
- `flux-1-dev` — highest quality (Black Forest Labs via NVIDIA cloud)
- `google-vids` — primary Google image generation path via google-accounting Python bridge
- `google-flow` — separate/manual Google Accounting endpoint, not the default automatic image path

### API Endpoint: `POST /api/images/generate/nvidia`

```json
{
  "prompt": "A futuristic city at sunset, cinematic lighting",
  "model": "FLUX.1-schnell",
  "width": 1280,
  "height": 720
}
```

### What happens at ingest
1. Image generated by selected model
2. SHA-256 hash computed, duplicates rejected
3. Image saved to `data/images/<prompt-slug>/<hash>.png`
4. `scripts/semantic_tagger.py` called with prompt + style:
   - **Taxonomy match** (YAML): subjects, tags, categories, mood
   - **YAKE/spaCy**: dynamic keyword extraction
   - **Ollama** (`gemma4:e4b`): generates `concept_tags`, `visual_objects`, `emotional_tone`
   - Builds `search_text_expanded` blob (used for FTS5/BM25 at query time — zero LLM)
5. `metadata.json` sidecar uploaded to Google Drive alongside the image
6. Record created in `media.db.sqlite` (`media_assets` table)

## Script-to-Images Pipeline (consolidated Giugno 2026)

> **Nota (Giugno 2026):** l'endpoint legacy `POST /api/script/generate-from-source` è stato **rimosso** nel consolidamento. La generazione script+immagini ora passa dall'endpoint unificato `POST /api/script/generate-from-clips` con la modalità clip-aware (caller passa `clip_ids`) o auto-search (`num_clips > 0` → `mediaCurator.Curate()`). I campi legacy **rimossi** (ritornano 400) sono: `visual_style`, `images_per_scene`, `width`, `height`, `scene_count`, `lines_per_image`, `render_video`, `video_style`, `video_transition`, `recommend_clips`, `agent_max_steps`, `agent_min_words`, `agent_batch`, `agent_model`. Il campo `style` del nuovo schema è **diverso** dal legacy `visual_style` (controlla i clip suggestions, non lo stile visivo delle immagini). Per il body schema canonico vedi `docs/CHANGELOG_2026-06-03.md` §0 e `AGENTS.md`.
>
> **Doc-fix (June 2026 reconciliation):** la nota sopra implica implicitamente che `/generate-with-images` sia stato "merged" in `/generate-from-clips`. Questo è impreciso — `/generate-with-images` esiste ancora come **endpoint dedicato e separato** (registrato in `handler_flow.go:153` accanto a `/generate-from-clips`), con handler `ScriptFlowHandler.GenerateWithImages` in `handler_generate_with_images.go` e request type `GenerateWithImagesRequest` in `types_clip_source.go:79`. **Condivide** con `/generate-from-clips` sia il job type (`script.generate_from_clips`) sia il worker (`HandleClipScriptGenerateJob` in `job_handler_clip_source.go`); la differenza è solo nel **preset del payload** che il handler applica forzatamente: `extract_entities=false`, `generate_scene_images=true`, `generate_metadata=false`. Vedi `docs/PARALLEL_IMAGE_GENERATION.md` §1.1 e `AGENTS.md` "Rule of thumb for new integrations" per il confronto sintetico.

### API Endpoint: `POST /api/script/generate-from-clips` (modalità clip-aware / auto-search)

```json
{
  "topic": "...",
  "source_text": "...",
  "language": "en",
  "tone": "documentary",
  "num_clips": 5,
  "clip_ids": [],
  "extract_entities": true,
  "artlist_search": true,
  "stock_search": false,
  "generate_metadata": true,
  "ordering_strategy": "scene"
}
```

**Parallel Execution & Performance:**
The image generation phase for scripts uses a concurrent worker pool (`concurrent.ParallelMap`) to generate scenes in parallel.
When using the Google Vids generator (`google-accounting` backend), the Python service maintains a Playwright session pool of pre-warmed browser instances per account, eliminating browser startup overhead.
The automatic image pipeline is intentionally anchored on Vids; Flow remains a separate manual/specialized endpoint.

See [`docs/PARALLELIZATION.md`](./PARALLELIZATION.md) for detailed architecture, configuration, and tuning guidelines.

## Video Animation (Zoom-Out)

```json

  "duration": 7
}
```

## Semantic Search Architecture

Images are searchable via **hybrid BM25 + vector search** with zero LLM at query time:

| Field | Source | Used for |
|-------|--------|---------|
| `search_text` | Taxonomy + YAKE | Basic FTS |
| `search_text_expanded` | LLM (Ollama, at ingest) | Full hybrid FTS blob |
| `concept_tags` | LLM (Ollama, at ingest) | Synonym/concept matching |
| `visual_objects` | LLM (Ollama, at ingest) | Object-level matching |
| `emotional_tone` | LLM (Ollama, at ingest) | Intent/tone matching |
| `embedding_json` | Sentence-Transformers | Vector cosine similarity |
